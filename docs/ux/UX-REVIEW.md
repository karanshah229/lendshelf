# LendShelf: independent review of UX-FLOWS.md

Reviewer's scope: `docs/ux/UX-FLOWS.md` (the "doc"), checked against `SPEC.md` §1, `src/`, `functions/src` and `firestore.rules`. The web build was not driven for this review; the doc and the code were the inputs. Doc line numbers refer to the file as reviewed (989 lines).

## Verdict

The v1.1 cut is mostly the right next build. The loan spine is the real problem in today's app, and the cut fixes it: Needs you on Home, Loans sorted by urgency, a Loan screen, the accept success sheet and invites. Keep it. It is not quite right in three ways:

- It leaves the C4.1 cold-start blocker half fixed. Invites ship, but the step that shows the inviter that a friend has joined (auto re-sync, G40) sits in the Phase 3 backlog.
- It is under-costed. Five items are rated M (2–4 days each) and seven are rated S (up to 1 day each), so the plan is about 17–27 developer-days before testing on Android, iOS and web. The doc says 3–4 weeks.
- Several of its "no backend" fixes only work if the right person opens the app at the right time.

**The single biggest risk is the "zero backend" rule itself.** To keep it, the cut relies on these client-side workarounds:

- pick-up flags kept on one device only;
- an undo made by delaying the server call by 6 s;
- watches created on the borrower's phone;
- guessing "lent to someone else" and "owner left" from other fields;
- an app-icon badge set by the app;
- closing a book that was never picked up with `confirmReturn`.

These workarounds send wrong pushes, such as "Thanks for returning" for a book that was never collected. They also leave the owner and the borrower seeing different states for the same loan, and they lose state when someone reinstalls the app. That is the "both sides always know the state" promise E4 is meant to keep. Four or five small backend changes (all S, most already written up as G34/G35/G36) would remove most of these workarounds. They cost less than the client code that works around them.
